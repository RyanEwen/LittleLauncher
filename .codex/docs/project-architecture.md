# Project architecture reference

Paths in this reference are relative to the LittleLauncher project unless stated otherwise.

## Architecture

- **Single-instance app** enforced via a named `Mutex` ("LittleLauncher"). A second launch signals the first instance via `PostMessage` with registered window messages (`LittleLauncher_ShowFlyout_{launcherId}`, `LittleLauncher_ShowSettings`).
- **Launchers** — users define one or more named `Launcher` objects (model: `LittleLauncher.Models.Launcher`). Each launcher has its own `Items` collection, tray icon (mode + optional custom path), and `NIconHide` visibility flag. Settings include a `Launchers: ObservableCollection<Launcher>`. On first run with old settings, the legacy `LauncherItems` list is migrated into a "Default" launcher.
- **Launcher kinds** — `Launcher.Kind` decides what the tray icon opens: `LauncherKinds.Items` (0, the default — a `FlyoutWindow` of launcher items) or `LauncherKinds.Web` (1 — a `WebFlyoutWindow` showing `Launcher.WebUrl`). **Never call `FlyoutWindow.Toggle` directly**: `Windows/LauncherPanels.cs` is the single place that resolves a launcher's kind, and every tray click, pinned shortcut and settings entry point routes through it.
- **MainWindow** is invisible (moved off-screen, 1×1). It owns one native tray icon per launcher via `Shell_NotifyIcon` (stored in `_trayIcons: Dictionary<string, TrayIconEntry>`). Uses `WS_EX_TOOLWINDOW` to hide from Alt-Tab.
- **FlyoutWindow** is a popup that displays launcher items. Supports two view modes per launcher: list view (icon + name side by side) and icon grid view (larger icon with name below, configurable icons-per-row wrapping grid). **A list column is as wide as the longest label the launcher holds**, capped at the 175px every column used to be and floored at 80, with one width shared by every column - ragged columns read as a broken table. `ComputeListColumnWidth()` decides it once per rebuild from measured label *strings*, never from laid-out content, and both the columns and the window sized around them read the cached answer. One instance is maintained per launcher (`_instances: Dictionary<string, FlyoutWindow>`), created up front by `WarmUp()` and parked off the virtual screen to compose its first frame — a window WinUI has never drawn presents a black rectangle when it is first shown. **Dismissing parks the window off the virtual screen rather than hiding it** (`ParkOffScreen`); `ShowWindow(SW_HIDE)` let WinUI release the composition surfaces, so the next cold open spent ~100ms re-rasterising every text run and item icon and the flyout slid in as an empty rectangle with the items popping in at the end. Because the window is therefore visible in the Win32 sense for the life of the app, **`_isOpen` — not `WS_VISIBLE` — is the test for "the flyout is open"**. Shown from a launcher's tray icon click, positioned above the taskbar, and when `UserSettings.FlyoutAnimationsEnabled` is on the full rendered window slides in and out from its anchored edge using short eased position updates, dismissed on focus loss or Escape. In icon mode, top-level groups are arranged by the custom `PackedIconPanel`, which lets narrower groups share a row beside wider groups while keeping row height based on the measured group content, and dragging near the flyout's left or right edge snaps the layout wider or narrower by whole icon columns and persists `Launcher.IconModeIconsPerRow` immediately.
- **Flyout edit mode** (`Windows/FlyoutWindow.EditMode.cs`) is where **all** launcher item editing happens. A hover-revealed pencil, the flyout's context menu, or **Edit items** on a launcher card enters it. A toolbar floats in its own window (`EditToolbarWindow`) above the flyout with add item/group/column, launcher settings and Done; group containers are tinted, empty groups and columns become drop targets, hovering shows a pencil overlay, the window border takes the accent colour, and drag-and-drop reordering and edge resize are enabled (both disabled outside edit mode). An empty launcher shows placeholder text explaining how to add items. Edit mode pins the flyout open — which is also what lets it accept **drops from outside the app** (`Windows/FlyoutWindow.ExternalDrop.cs`): files, folders, shortcuts and browser links dragged in from File Explorer, the desktop or a browser become items at the hovered position, mapped by `Services/DroppedItemFactory.cs`. The Windows 11 Start Menu is not a usable drag source — see [.codex/docs/drag-drop.md](drag-drop.md). **Geometry contract:** it may grow the flyout's height but must never change its width or the size of any item or group — see [.codex/docs/drag-drop.md](drag-drop.md). Item/group edits use owned windows (`ItemEditorWindow`, `TextPromptWindow`, `LauncherSettingsWindow`) rather than `ContentDialog`, which cannot overflow the flyout's HWND.
- **WebFlyoutWindow** (`Windows/WebFlyoutWindow.cs`) is the flyout a web launcher opens: a borderless, always-on-top, tray-anchored window hosting a **WebView2** on the launcher's URL, with a slim header (back, forward, reload, a **"…" menu** of per-moment options, **zoom** among them, an **Advanced** submenu (developer tools, reload ignoring cache, turn on notifications, rebuild this launcher's notification bridge or every launcher's) and launcher settings at its foot, open in browser, pin, minimize in regular-window mode only, maximize, close), a **tab strip** and an optional address bar beneath it (`Launcher.WebShowAddressBar`, off by default — the "…" menu carries the setting). **Every browser it owns is a tab** (`Windows/WebFlyoutWindow.Tabs.cs`): a link asking for a new window becomes one rather than leaving for the real browser, and the strip appears on its own once there are two (or always, under `Launcher.WebAlwaysShowTabs`). Tabs the *launcher* owns — its address, or each bookmark under `WebBookmarksAsTabs` — are the only ones allowed to write its icon or be re-navigated by a settings change; a tab opened from a link is the user's own place and nothing configured may move it. It presents like `FlyoutWindow` but its resource model is the **opposite**: nothing is created until the user first opens it (it is deliberately excluded from `WarmUp`), and dismissing it collapses the control, calls `CoreWebView2.TrySuspendAsync()` and drops `MemoryUsageTargetLevel` to `Low` — except under `WebHiddenPolicies.KeepRunning`, which only collapses, because both the memory hint and Chromium's background throttling stop a hidden page receiving at all (the throttling is disabled for the whole environment in `Services/WebViewEnvironments.cs`). Under the default `WebHiddenPolicies.UnloadWhenIdle` the whole browser is then closed after `Launcher.WebIdleUnloadMinutes`, so a hidden dashboard costs nothing at all. Each web launcher gets its own WebView2 user-data folder (`%AppData%\LittleLauncher\WebProfiles\{launcherId}`), so logins survive restarts and launchers stay signed in independently. **Camera, microphone, location and notification requests are answered in the flyout's own prompt bar** and remembered per profile (`Windows/WebFlyoutWindow.Permissions.cs`) — there is deliberately no "trust this site" shortcut, because a site handed a grant it never asked for skips the flow that grant implies, and for notifications that flow is what registers the push worker; **Turn on notifications** makes a site that will not ask call `requestPermission()` rather than writing the permission behind its back; page notifications become Windows toasts — each carrying a **header with its launcher's name**, so Notification Center files them under the launcher rather than under the app, and each **withdrawn again** when the page closes the notification, when the launcher is brought to the front, when its header is clicked, when the launcher is deleted, or on the next reboot. A launcher also holds at most five at once, because the Action Center queue is per *app* and every launcher shares one, so a launcher that withdraws nothing evicts the rest — and since a suspended or unloaded browser raises none, granting notifications *offers* to switch that launcher to `WebHiddenPolicies.KeepRunning` rather than doing it silently. **WebView2 surfaces only non-persistent notifications**, so the page's `showNotification` is rewritten to that flavour, and the service worker — which a document script cannot reach — is bridged by serving the shim followed by the site's own script **inlined** as it is fetched (`WebFlyoutWindow.ServiceWorker.cs`), which is also what makes toast **action buttons and inline reply** run the app's own `notificationclick` handler. **The wrap can never `importScripts` the URL it is served at** — that resolves out of the registration's script resource map, which already holds the wrap, so it imports itself until the stack gives out — and a site that serves its worker only to a request carrying `Service-Worker: script` (Messenger) needs that header put on through the DevTools protocol, since a page is forbidden from setting it. The window is fully borderless (no non-client area), so it has no system sizing border: resizing is done with invisible XAML edge/corner grips that drive `SetWindowPos` and persist the dragged size onto the launcher. **Maximize is temporary** — the header's maximize fills the monitor's work area and is dropped on dismissal, so it is never written to the launcher. **Double-clicking the caption does the same thing in both directions**, the caption being the three strips that already drag the window (header, empty tab strip, empty bookmark bar); it is counted inside `BeginWindowMove` against the system's own double-click time and slop, because those strips take their own `PointerPressed` and XAML then raises no tap gestures. **Resting on that button** instead drops a picker of places to send the window, drawn as a 3x3 grid of little screens the way Windows 11 hangs snap layouts off the same button. It **moves the window and writes nothing** - it borrows nine of the presets the "Opens at" setting uses and shares only their labels with it. The other two anchors are rules about opening rather than places, so they stay in the menu. **Always-on-top is a band, not a place**: several launchers can be in it at once, so the one that takes focus re-asserts its place at its head (`RaiseWithinTopmostBand`) and `SetTopmost` refuses to re-apply a value the window already has, or a background favicon fetch on one launcher pushes it in front of the one being read. **A web launcher is a home page plus a bar of bookmarks.** `Launcher.WebHomeUrl` is where it opens and is a setting of its own, not a position in the bar (an earlier design made it the first bookmark; folders ended that, since position zero can hold something with no address). Empty falls back to the first bookmark, so files written before it behave unchanged, and a bookmark holding the same URL is an ordinary bookmark nothing tries to merge. Read it through `Launcher.WebAddress`. The bar appears as soon as there is a second bookmark (`Launcher.ShowsBookmarkBar`), with no setting behind it. **The bar takes folders** (`WebBookmark.IsFolder` + `Children`, the same shape a group takes in an item launcher): one draws with a folder glyph, opens a menu of what it holds, nests without a depth limit, accepts a bookmark dropped onto it or filed through **Move to folder**, and gives its contents back to the bar when removed. **The bar otherwise holds no state** (`Windows/WebFlyoutWindow.Bookmarks.cs`): it opens pages the way a browser's does — a click loads the bookmark in the tab in front, a middle-click or Shift/Ctrl-click opens a new tab, clicking the bookmark for the page already showing simply loads it again, and nothing in the bar is tinted. There is no collapsed state and no per-bookmark browsers; extra tabs are made only by the gestures that ask for one. **It is also edited from the bar**: a star at the end of the address bar adds or removes whatever the address box shows (the "…" menu carries the same action, since the address bar is off by default), right-clicking a bookmark opens it (here or in a new tab), renames, re-addresses, copies, defaults, moves or removes it, and dragging one reorders the bar, and the bar's own menu carries **Icons only**, the launcher-wide switch that drops every label. Launcher settings still holds the full list. See [.codex/docs/web-launchers.md](web-launchers.md).
- **SettingsWindow** is a WinUI 3 window with `MicaBackdrop`. It uses `NavigationView` with page-based navigation (Home, Launchers, Cloud Sync, Settings, About). The Launchers page shows launcher cards with a Settings button (opens `LauncherSettingsWindow`) and an Items row (item count + a bulk-ops menu: export, import, import bookmarks — the bookmark selector is searchable). Creating a new launcher auto-opens launcher settings. **There is no in-settings item editor** — all item editing happens in the flyout's edit mode.
- **Settings** are serialised to `%AppData%\LittleLauncher\settings.json` via `System.Text.Json`, managed by the fully static `SettingsManager`. On first load, migrates from legacy `settings.xml` (XmlSerializer) to JSON.
- **Global sync** moves all launchers (as `launchers.json`) between machines, and is **transport-pluggable**: `UserSettings.SyncProvider` (see `Models/SyncProviders.cs`) selects SFTP (0, the default), OneDrive, Google Drive, a network file share, any other folder, or any WebDAV server. `LauncherSyncService` is the only entry point — it resolves the provider and dispatches to `SftpSyncService` (SSH.NET), `CloudSyncService` (a signed-in cloud account), or `FolderSyncService` (a directory, in `UserSettings.SyncFolderPath`). **OneDrive and Google Drive use their vendor APIs — Microsoft Graph and Drive v3 — not synced folders**, so the upload is confirmed by the service, no sync client need be installed, and the remote's modified time can be read; each signs in through the system browser via `OAuthPkceClient` and stores tokens DPAPI-encrypted in `CloudTokenStore`, never in settings.json. **WebDAV** (Nextcloud, ownCloud, a NAS) rides the same `ICloudFileStore` path but with Basic-auth credentials typed into the app rather than a browser flow — no registration, consent screen or vendor review, because it is a standard rather than a product. Adding another account provider means implementing `ICloudFileStore` and nothing else. Folder providers serve everything else — Dropbox, Seafile, Syncthing, and OneDrive for Business, which cannot use the app-folder permission. **Never call a transport directly from outside `Services/`** — and never gate a trigger on `SftpHost`, which is meaningless under any other provider. The wire format, the newer-local download guard, the merge and the atomic write live in `LauncherPayload` so the transports cannot drift apart. See [.codex/docs/sync.md](sync.md).
- **SftpSyncService** also handles per-launcher shared sync, which is a separate feature with its own per-launcher transport (`Launcher.SharedSyncMode`: file path or SFTP) and is unaffected by `SyncProvider`. Its transport is `Launcher.SharedSyncMode` (`Models/SharedSyncModes.cs`): File (0), SFTP (1) or WebDAV (2) — **WebDAV is the cleanest for person-to-person sharing**, since the URL is already a shared address and both sides can write. The cloud-account providers are deliberately absent: OneDrive's app folder and Google's app-data folder are private per-user storage that cannot be granted to anyone else. It supports 1-way (owner pushes, subscribers pull) and 2-way (all participants push and pull, last save wins) modes. `AutoSyncService` skips automatic downloads while local launcher item edits are still pending upload so periodic syncs do not overwrite newer local flyout/editor changes. A merge leaves a launcher's `Items` untouched unless the download differs (`LauncherPayload.ItemsMatch`) and rebuilds the flyout of any launcher whose items it did replace, because **a flyout's rows hold the item objects themselves** and equal-valued copies leave remove, move and edit looking up items the launcher no longer contains. Periodic/shared downloads then refresh flyouts via `FlyoutWindow.InvalidateItems(force: false)` and `WebFlyoutWindow.InvalidateBookmarks()` (a merge hands the launcher new `WebBookmark` objects, so a bar built before the sync is left holding bookmarks the launcher no longer contains) — a no-op sync then skips the rebuild instead of tearing down and re-creating every flyout's visual tree on a timer (that unnecessary rebuild churn drove a large container-leak; see [.codex/docs/drag-drop.md](drag-drop.md)).
- **Taskbar jump lists** (`Services/JumpListService.cs`) put a launcher's own contents on the menu Windows shows when its **pinned taskbar button is right-clicked**: its items, flattened exactly as the flyout flattens them, or its bookmarks for a web launcher. **The list belongs to an AppUserModelID rather than to a process**, which is what allows one per launcher: `Launcher.PinAumid` already records one per pinned launcher, and for launchers pinned before the app recorded it, the taskbar's own pin store is read as a fallback (for publishing only, never as window identity). **Nothing published can be a live menu** - the shell never says a jump list was opened - so it is republished on `SettingsManager.Saved`, debounced, and skipped when the resulting list is unchanged. A **web launcher with a single address publishes nothing**, since its one entry would go exactly where clicking the button already goes. Every task runs the companion exe with a position and a **token identifying the entry by content**, so a list left over from before an edit either finds its entry or falls back to opening the launcher, and a **bookmark opens in a new foreground tab** rather than taking over whatever the launcher was left on. **Below a separator sit the launcher's own commands** (`Models/LauncherActions.cs`): launcher settings, edit items or open in browser depending on kind, and the app's settings. They are never what gets trimmed when Windows is short of room, and a launcher with nothing to list still gets them. **The heading is Windows' word "Tasks" and cannot be changed** - see [.codex/docs/pinvoke.md](pinvoke.md).
- **LauncherShortcut** (`LittleLauncherFlyout.exe`) is a companion exe pinned to the taskbar. It signals the main app via `PostMessage` with a launcher-specific message (`LittleLauncher_ShowFlyout_{launcherId}`) then exits. Accepts `--launcher {guid}`, `--name {name}`, `--icon {path}`, `--aumid {id}`, and `--pin` arguments (also supports legacy `--layout` for backward compat). `--item {index} --token {n}` is what a jump list task runs: it posts `LittleLauncher_LaunchItem_{launcherId}` instead of the show-flyout message, and `Windows/LauncherPanels.cs` resolves the entry. **`--aumid` is the pin's AppUserModelID, minted by the main app** and stored as `Launcher.PinAumid` — the companion mints its own only as a fallback, because the identity has to be written down somewhere and this process exits as soon as the pin is made. In `--pin` mode, sets relaunch properties (`PKEY_AppUserModel_ID`, `RelaunchCommand`, `RelaunchIconResource`, `RelaunchDisplayNameResource`) on the MessageBox HWND for taskbar pinning identity. AUMID format: `LittleLauncher.Launcher.{guid}.{TickCount64}` (unique per pin attempt to bust per-AUMID icon cache). Release builds are Native AOT for instant startup — see the performance warning in `ARCHITECTURE.md`.

## Key namespaces

| Namespace | Contents |
|---|---|
| `LittleLauncher` | App, MainWindow, SettingsWindow |
| `LittleLauncher.Classes` | NativeMethods, ThemeManager, IconGallery, ShellIcons, WindowChrome, ExpanderReveal |
| `LittleLauncher.Classes.Settings` | SettingsManager |
| `LittleLauncher.Controls` | PackedIconPanel, TabStripPanel (the tab strip's squeeze-to-fit row), OverflowStripPanel (the bookmark bar's row, and how many bookmarks it could not fit) |
| `LittleLauncher.Models` | LauncherItem (its `ToString()` is the accessible name for every flyout row), Launcher, WebBookmark, BrowserExtension, SshConnectionProfile, SyncProviders, SharedSyncModes, LauncherActions (the numbered commands a taskbar jump list carries through the companion exe) |
| `LittleLauncher.Pages` | All settings pages, LauncherBulkOps (item export/import, bookmark import), BookmarkPicker (searchable single-bookmark chooser, in a `ContentDialog` for full-size windows) and BookmarkPickerView (the chooser itself, with no opinion about its host) |
| `LittleLauncher.Services` | LauncherSyncService (global-sync entry point), SftpSyncService, CloudSyncService (+ `ICloudFileStore`, OneDriveFileStore, GoogleDriveFileStore, WebDavFileStore, OAuthPkceClient, ProtectedStore, CloudTokenStore, CloudSyncCredentials), FolderSyncService, CloudFolderService, LauncherPayload, AutoSyncService, FaviconService, UpdateService, AppPickerService, AppCatalog, BrowserCatalog, BookmarkImport, DroppedItemFactory, StartMenuShortcutService (per-web-launcher Start Menu shortcuts), WebProfileCleanupService (finds and deletes WebView2 profile folders nothing points at), JumpListService (the taskbar jump list on each pinned launcher's button), WebViewEnvironments (one CoreWebView2Environment per user-data folder, shared by every browser on it), BrowserExtensionService (the extension list, CRX/ZIP unpacking, and loading them onto each profile) |
| `LittleLauncher.ViewModels` | UserSettings, AppPickerEntry |
| `LittleLauncher.Windows` | FlyoutWindow (+ `FlyoutWindow.EditMode.cs`, `FlyoutWindow.ExternalDrop.cs`), WebFlyoutWindow (+ `WebFlyoutWindow.Tabs.cs` — every browser the flyout owns, the tab strip, its per-tab right-click menu and new-window handling; `WebFlyoutWindow.Permissions.cs` — site permissions and page notifications; `WebFlyoutWindow.ServiceWorker.cs` — the service-worker bridge, notification actions and inline reply; `WebFlyoutWindow.TaskbarButton.cs` — regular-window mode, its taskbar button and pin identity; `WebFlyoutWindow.MoreMenu.cs` — the header's "…" menu of per-moment launcher options; `WebFlyoutWindow.PositionPicker.cs` — the graphical anchor picker that drops out of the maximize button on hover; `WebFlyoutWindow.Bookmarks.cs` — the bookmark bar, and adding, editing, reordering and removing bookmarks from inside the flyout; `WebFlyoutWindow.Shortcuts.cs` — the browser keyboard shortcuts and the sheet that lists them; `WebFlyoutWindow.Extensions.cs` — catching a store install and standing in for the missing extension toolbar; `WebFlyoutWindow.Session.cs` — the tabs a launcher had open, restored on its next open; `WebFlyoutWindow.BrowserPages.cs` — the `chrome://`/`search://` addresses a real browser answers and WebView2 does not; `WebFlyoutWindow.StripDrag.cs` — the drag source a `Button` cannot be on its own, shared by the tab strip and the bookmark bar; `WebFlyoutWindow.FolderPopup.cs` — the bookmark-folder lists, drawn as an overlay in the window's own tree because a `Popup` can never receive a drag), LauncherPanels, EditToolbarWindow, ItemEditorWindow, TextPromptWindow, LauncherSettingsWindow, ShortcutsWindow, ExtensionPopupWindow (an extension's own popup, and the window an extension gets when it asks for one), BookmarkPickerWindow (the browser-bookmark chooser, for the flyout, which cannot host a `ContentDialog`) |

**Note:** The `LittleLauncher.Windows` namespace shadows the WinRT `Windows.*` namespace. Use `global::Windows.` prefix when accessing WinRT types (e.g. `global::Windows.Graphics.PointInt32`).

**Note:** `LittleLauncher.Models.Launcher` conflicts with other framework types. Use `using Launcher = LittleLauncher.Models.Launcher;` at the top of any file where disambiguation is needed.
